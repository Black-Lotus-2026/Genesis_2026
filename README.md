# Умный роутинг выплат (Smart Payout Routing Engine)

Автономный сервис интеллектуальной маршрутизации выплат между платёжными провайдерами с поддержкой каскадирования, контролем жёстких ограничений (Hard-constraints) и динамическим распределением трафика (Soft-goals).

---

## 1. Что реализовано на текущий момент

### 1.1. Архитектура и модульность
Решение разделено на независимые компоненты:
* **`HardConstraintsFilter`**: Модуль валидации обязательных бизнес-правил и отсева недопустимых кандидатов.
* **`PaymentRouter`**: Основной движок маршрутизации, управляющий каскадом попыток, приятием решений и сохранением состояния.
* **`StateTracker`**: Отслеживание динамических параметров провайдеров в процессе обработки очереди (накопленный дневной оборот `daily_approved_amount`, счётчик обработанных операций `processed_count`).
* **Модуль отчётности**: Автоматическая генерация `routing_report.json` со срезом утилизации лимитов, причин отклонений и рекомендациями.

### 1.2. Поддержка Hard-Constraints (Жёсткие ограничения)
Перед рассмотрением провайдера проверяются строгие правила допуска:
* **Статус провайдера**: исключение неактивных (`status != 'active'`).
* **Диапазон суммы чека**: валидация попадания в интервал `[limit_amount_min, limit_amount_max]`.
* **Дневной лимит оборота**: контроль `daily_approved_amount + amount <= daily_amount_limit`.
* **Лимиты одновременных операций**: проверка по количеству (`in_progress_count`) и сумме (`in_progress_amount`).
* **Банковский фильтр**: проверка поддержки банка получателя (`banks`) с учётом флага `exclude_banks`.
* **Маржинальность**: проверка неотрицательной маржи (`provider_margin_pct <= merchant_margin_pct` либо флаг `allow_negative_agreement`).
* **Доступность реквизитов**: проверка наличия свободных реквизитов (`available_requisites > 0`).
* **Нулевая доля трафика**: провайдеры с `traffic_percentage == 0` исключаются из основного пула (за исключением fallback-шлюза).

### 1.3. Полная объяснимость решений (Explainability & Audit Log)
Для каждой транзакции формируется массив `attempts`:
* Для каждого отсеянного провайдера фиксируется решение `"decision": "skipped"` и точная стандартизированная причина (`amount_exceeds_limit`, `amount_below_minimum`, `bank_not_in_list` и др.).
* Для выбранного провайдера фиксируется `"decision": "selected"` с причиной (`only_eligible_provider`, `first_eligible` или fallback).
* Поддерживается fallback на шлюз `spacepayments`, если ни один внешний партнёр не удовлетворяет условиям.

### 1.4. Соответствие требованиям валидатора
* Решения по всем заявкам формируются в `routing_decisions.json`.
* Скрипт валидации организаторов `validate_10.rb` проходит без ошибок и предупреждений (29/29 проверок успешно, детерминированные кейсы строго соблюдены).
